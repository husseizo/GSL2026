# DGX Prototype 1.5 — Decision Log

Short entries — the reasoning behind choices that weren't the only reasonable option. Same format as [docs/ai/decision-log-catalogue-rag.md](../ai/decision-log-catalogue-rag.md) and the phases before it.

## Why `CatalogueRagService` composes low-level primitives directly instead of calling `RagService.retrieveAndGenerate()`

Prototype 1's generative path called `RagService.retrieveAndGenerate()` as one opaque method — no seam existed for grouping context by evidence quality, running claim verification against the real evidence text, or requesting structured JSON output specific to the catalogue domain. Rather than adding catalogue-specific parameters to the shared `RagService` (which would risk changing behavior for every other assistant that calls it), `CatalogueRagService` now calls `AiGatewayService`/`VectorSearchService`/`PromptRegistryService` directly — the same real primitives `RagService` itself uses, just composed differently. `RagService` is completely unchanged and still serves technician/parts/lubricant/manager assistants exactly as before.

## Why the structured-answer JSON schema asked of the model is narrow, not the full spec-listed schema

The full schema the spec describes (`answer, matchedProducts, matchBasis, verifiedFacts, possibleMatches, alternatives, fitment, conflicts, missingInformation, warnings, citations, confidence, recommendedHumanAction`) has many fields that are pure derivations of what was already retrieved (which chunks are verified vs. candidate, which have a live conflict) — asking a small, locally-hosted 7-8B model to correctly populate all of them in one JSON response, on the first attempt, with no schema-conformance guarantee beyond Ollama's `format: "json"` (valid JSON syntax, not schema validation), was judged likely to produce a much higher structured-output failure rate than asking for a narrow `{answer, citedDocumentIds, hasConflict, missingInformation}` object and deriving the rest from real application-side data. This was a judgment call, not something separately A/B-tested this phase (a real gap, noted rather than hidden).

## Why `format: "json"` was added to the DGX FastAPI service rather than left unused

Ollama's `/api/generate` endpoint natively supports a `format` parameter constraining decoding to valid JSON. The DGX service's Python `GenerateRequest`/`GenerateResponse` models didn't expose it. Adding an optional `format: Optional[str] = None` field (default unset, identical behavior for every existing caller) and passing it straight through to Ollama when set is a small, additive, backward-compatible change — not a redesign of the inference boundary's contract.

## Why the confidence-model bug (candidate metadata used as a relevance proxy) was worth documenting at length

This bug directly explains part of Prototype 1's own NEEDS_TUNING finding: a system that can accidentally report MEDIUM confidence for a genuinely irrelevant query (because the one document in a small corpus happens to be marked verified) is exactly the kind of overconfidence the spec's whole confidence-calibration section exists to catch. Finding and fixing it via the pre-existing integration test (not a new one written to catch it) is real evidence that Prototype 1's own test suite was doing its job — the bug was introduced by this phase's own rewrite, and caught by this phase's own pre-existing regression test, the same day.

## Why the full platform-wide integration suite was terminated rather than awaited

See [docs/ai/final-prototype-report.md](../ai/final-prototype-report.md)'s addendum for the full incident: a full, unscoped `npm run test:integration` run was left executing for hours while several *targeted*, scoped integration runs were launched afterward in the same session — each one's `test-global-setup-integration.ts` truncates the entire shared test database at its own start, invalidating whatever the original full run would have measured. It was killed rather than left to report a misleading result. The lesson (never run a scoped integration suite while an unscoped one is still executing against the same database) is now documented in [operational-runbook.md](../ai/operational-runbook.md)-equivalent guidance for this phase.

## The real root cause of "hung" integration runs — a Redis connection leak, not a stall

The catalogue-ai-scoped integration suite appeared to hang for hours multiple times during this phase, always assumed (reasonably, given the shared-database-truncation incident above) to be some kind of stall or contention. Direct process inspection eventually showed the actual test run completed successfully every single time, in ~80 real seconds — the Jest *worker process* simply never exited afterward, with Jest's own diagnostic message ("Jest did not exit one second after the test run has completed... asynchronous operations that weren't stopped") going unnoticed in piped, buffered output.

Root cause: `catalogue-rag.integration-spec.ts` (written this phase) instantiated `new RedisService()` directly but never closed it in `afterAll()` — a real, open `ioredis` TCP connection with no automatic reconnect (by design — `retryStrategy: () => null`) keeps Node's event loop alive indefinitely if never explicitly disconnected. Fixed by capturing the instance and calling `redis.onModuleDestroy()` in `afterAll()`, matching the pattern `catalogue-search.integration-spec.ts` already used correctly.

While fixing this, the exact same pre-existing bug (not introduced this phase) was found in `api-platform.integration-spec.ts` — a file this phase never touched. This retroactively explains why the *original* full-platform integration run (from the Prototype 1 acceptance phase, see the addendum above) never completed either: it likely wasn't only the database-truncation collision, but this same class of leak in at least one file along the way. Fixed the same way; confirmed with a real, direct run (`EXIT_CODE=0`, clean process exit, in ~7 real seconds).

The general lesson: **a Jest integration spec that creates any real, unmanaged connection (Redis, a raw TCP client, a file handle) must close it in `afterAll()`, even when the test itself doesn't seem to need explicit cleanup to pass** — the tests will report green regardless; only the process's own exit behavior reveals the leak, and that signal is easy to miss in piped/buffered output (see the equivalent lesson in [operational-runbook.md](../ai/operational-runbook.md)).

## Why reranker/embedding/LLM-model comparisons are scoped down, honestly

One embedding model (`nomic-embed-text`) and one generation model (`llama3`) are locally available in this environment; no cross-encoder reranker model is available either. Rather than fabricate multi-model comparison numbers, this phase implements the comparison *infrastructure* (a real RRF reranker function, a real calibration-metrics module, a documented mechanical path to add a second model via `ollama pull`) and reports honestly that the comparisons themselves are single-candidate in this environment — exactly the same discipline Prototype 1 applied to the same constraint.

## Why context minimization defaults stayed at 5 (Baseline A's width) rather than moving

The real context-size sweep (1/3/5/8) run this phase did not produce clear, decisive evidence that a different default improves groundedness/citation-correctness enough to justify a change, on the current small real evaluation sample. Changing a production default without decisive evidence, just because a sweep was run, would be tuning by motion rather than by evidence — the spec's own instruction is "tune weights using evaluation data, not intuition alone," which cuts both ways: no evidence for a change is itself evidence to keep the current default.

## A real query-classification bug found by the multilingual benchmark step, not by unit tests

The 40-step verification script's multilingual step (step 27) ran a real Swahili-mixed query embedding a real OEM number (`Nataka sehemu yenye namba 036145933G`) and found the OEM number did **not** survive in the final answer. Investigating live (not just re-reading the script output) showed the actual behavior: `classifyQuery()`'s `IDENTIFIER_PATTERN` only matches when the *entire* trimmed query looks like an identifier, gated further by `wordCount <= 3` — so an identifier embedded inside a longer sentence, in any language, never triggered deterministic lookup at all. The query fell straight to semantic `DESCRIPTION` search, which for this exact identifier surfaced five unrelated documents ("Mounting, engine" / "Sensor, exhaust gas temperature"). Claim verification then did its job *correctly* — it found the model's mention of the real OEM number was not supported by that (wrong) retrieved evidence, and stripped it, producing an honest but unhelpful "insufficient evidence" refusal for a query the system should have answered deterministically.

This existing unit-test suite did not catch it because a test at `query-understanding.spec.ts` explicitly asserted the buggy behavior as intended ("classifies a Swahili sentence containing a real OEM number as DESCRIPTION — too many words for the identifier heuristic"). It surfaced only through a real, live query against the live database during verification.

Fixed by adding a second-stage check in `classifyQuery()`: when the whole-string checks find nothing, scan the query's individual words for one matching a stricter embedded-token pattern (`(?=.*[A-Za-z])(?=.*\d)[A-Za-z0-9.-]{5,17}`, i.e. a token with both a letter and a digit, 5–17 characters) and, if found, still route to `IDENTIFIER` with that token as `candidateIdentifier`. This is safe by construction: `ask()` already falls through to semantic search if deterministic lookup finds nothing for the candidate, so a false-positive embedded-token match (e.g. "500ml" in "500ml bottle") costs one harmless extra lookup, not a wrong answer — the same over-inclusion tradeoff the original whole-string `IDENTIFIER_PATTERN` already makes deliberately (see its own comment). Verified: the exact same live Swahili query that previously produced an incorrect refusal now returns the correct deterministic `EXACT_OEM` match (`V-Ribbed Belt`, confidence `VERIFIED`, zero claims removed). The stale unit test was corrected to assert the fixed behavior, plus a new test for picking the longest of multiple embedded candidates.

**A known, honestly-scoped remaining gap**: the fix above only extracts a single contiguous alphanumeric token. The offline evaluation dataset's own SWAHILI_MIXED case uses a *space-separated* OEM number (`"164 440 52 41"`, all digits, no letters) — this doesn't match the embedded-token pattern (which requires a letter, to avoid misclassifying an ordinary number-with-spaces in prose as an identifier) and isn't a single token to begin with. Detecting a run of consecutive short numeric groups as one split identifier is a materially harder normalization problem, and was not attempted this pass — noted honestly rather than silently left unfixed-looking-fixed.

## A real CORS gap found via live browser testing of the Web Portal — not an AI-tuning change

Found while helping the user actually log into the Web Portal at `localhost:5174` with a freshly-created account: the login call failed in the browser with a generic "Failed to fetch," even though the identical request via `curl` worked correctly (`201 Created`). `curl` isn't subject to same-origin policy; a browser is. `src/main.ts` never called `app.enableCors(...)` — Nest's default is CORS disabled — so the browser silently blocked the cross-origin request (portal origin `http://localhost:5174`, API origin `http://127.0.0.1:3900`) before it ever reached the server. This explains why every credential check this phase (all done via `curl`) looked fine while the actual portal login never could have worked.

Fixed by adding `app.enableCors({ origin: [...four known local dev origins...], credentials: true })` in `main.ts`, scoped to the real dev ports (`localhost:5174`/`:5180`, `127.0.0.1:5174`/`:5180`), not a wildcard. Verified live: an `OPTIONS` preflight from `Origin: http://localhost:5174` now returns `204` with `Access-Control-Allow-Origin: http://localhost:5174`, and the real `POST /auth/login` response carries the same header with `201 Created`. `tsc --noEmit` clean.

This is explicitly **not** a change to the model, prompt, retrieval weights, corpus, index, decoding settings, context limits, or evaluation dataset — it's an API/portal connectivity defect fix, orthogonal to the frozen Baseline-A-vs-tuned comparison, and does not require re-running the evaluation harness.

## A real, small-sample-size limitation surfaced by the same NO_ANSWER-exclusion fix — decoding-settings comparison is not actually decisive

Fixing the groundedness/citation/unsupported-claim averages to exclude zero-evidence NO_ANSWER cases (see the eval-methodology entry near the top of this log) had a side effect worth reporting honestly: it leaves exactly **one** real generative case counted in those averages on the current dataset — the SWAHILI_MIXED case above, whose space-separated OEM number is the known gap just described, so it still falls through to imprecise semantic search rather than deterministic lookup. Running the real temperature-0-vs-0.3 decoding comparison (`scripts/_tmp_decoding_compare.ts`, executed live against the running DGX service) produced byte-identical generation metrics at both temperatures (`avgGroundedness: 0, avgUnsupportedClaimRate: 0, avgCitationCorrectness: 1` for both). This is not evidence that temperature doesn't matter — it's an artifact of n=1: with only one real evidence-bearing generative case in the officially-APPROVED set, there is no statistical basis to draw a temperature conclusion either way. The default (temperature 0, deterministic) is kept for the same reason context width was kept at 5: no decisive evidence for a change is itself evidence to keep the current, more conservative default for a catalogue-answering assistant — not because the comparison was decisive.
