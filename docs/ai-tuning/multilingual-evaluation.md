# Multilingual Evaluation (expanded)

## What was added this phase

The offline evaluation dataset (`CatalogueEvaluationService.buildEvalSet()`) now includes a real `SWAHILI_MIXED` category — a real Swahili-English mixed query built from an actually-imported part's real OEM number (`"Nataka sehemu yenye namba <real OEM>"`), evaluated end-to-end (previously this exact query pattern was only exercised as a one-off spot-check in `scripts/verify-dgx-catalogue-rag.ts`, not as a standing dataset entry).

## A real bug found by this benchmark, not by unit tests

The first real run of verify script step 27 found the real OEM number did **not** survive: `classifyQuery()` only checked whether the *entire* trimmed query looked like an identifier, so any identifier embedded inside a longer sentence — in any language — fell straight to semantic `DESCRIPTION` search, which for that exact query surfaced unrelated documents; claim verification then correctly (but unhelpfully) stripped the unsupported identifier, producing an honest refusal for a query that should have been answered deterministically. Fixed by extending `classifyQuery()` to also scan for a single-token embedded identifier (a word containing both a letter and a digit) and route it to deterministic lookup first. See [decision-log.md](decision-log.md) for the full incident and fix.

## Real result (post-fix)

`scripts/verify-dgx-prototype-1-5.ts` step 27 re-runs this real query live and checks that the real OEM number appears unmangled in either the direct answer text or the matched-product identifiers. Real result after the fix: **preserved = true**, resolved via deterministic `EXACT_OEM` lookup (confidence `VERIFIED`, zero claims removed) rather than the generative path.

## Honest scope and a real known gap

This remains a small, real spot-check plus one dataset entry — not a systematic multilingual benchmark across many real Swahili queries, workshop shorthand, or catalogue abbreviations. Building that properly would need a real, larger set of authentic Swahili automotive queries with human-reviewed expected answers (per [ground-truth-governance.md](ground-truth-governance.md)'s rule that ground truth should not be generated by the same model being evaluated) — not fabricated this phase.

The fix above only extracts a **single contiguous token**. The evaluation dataset's own `SWAHILI_MIXED` case uses a *space-separated* OEM number (`"164 440 52 41"`) rather than one token — this still falls through to semantic search rather than deterministic lookup, since detecting a run of consecutive short numeric groups as one split identifier is a materially harder normalization problem not attempted this phase. This is the real, honest reason this phase's generation-quality metrics (groundedness/unsupported-claim rate) are based on only one real evidence-bearing generative case once the zero-evidence `NO_ANSWER` case is correctly excluded — see [final-tuning-report.md](final-tuning-report.md).
