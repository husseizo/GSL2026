# Data Validation, Business Baselining & AI Readiness — Decision Log

Short entries — the reasoning behind choices that weren't the only reasonable option. Same format as [docs/data-consolidation/decision-log.md](../data-consolidation/decision-log.md) and the root [decision-log.md](../architecture/decision-log.md).

## Why several proposed models were folded into fields on existing/other models, not built as separate tables
The original brief proposed roughly 25 new tables (`SourcePriority`, `ReviewPriority`, `ReviewEvidence`, `ReviewQualityCheck`, `ReviewUndoRequest`, `SourceBranch`/`SourceWarehouse`/`CanonicalBranch`/`CanonicalWarehouse`, `BaselineSegment`/`BaselineEvidence`/`BaselineApproval`/`BaselineVersion`, and more). Each one was checked against a real question: does this concept ever need independent multiplicity from the model it would attach to? `ReviewEvidence`/`ReviewQualityCheck` — no, a decision has exactly one evidence bundle and one quality check, so they're fields on `ReviewDecisionDetail`. `SourceBranch`/`SourceWarehouse`/`CanonicalBranch`/`CanonicalWarehouse` — the Data Consolidation phase already built `WarehouseExternalReference`/`BranchExternalReference` for exactly this mapping; extending them with `mappingConfidence`/`evidence`/`reviewedById` covers the same real requirement without four new tables. `BaselineSegment`/`BaselineEvidence`/`BaselineApproval`/`BaselineVersion` — all fields on `BaselineMetric`/`BaselineRun`/`BaselineDefinition`. This mirrors the exact discipline already established in the Data Consolidation phase (folding `ImportBatchItem` into `RawSourceRecord`, merging `SourceSnapshot`+`SourceSchemaSnapshot`) — consistency of approach, not a new philosophy.

## Why `ManualReviewItem`, `WarehouseExternalReference`, `BranchExternalReference`, and `ForecastRun`/`ForecastMethod` were extended in place rather than replaced
The phase's mandatory principles are explicit: "preserve... manual-review safeguards" and "do not duplicate existing... modules." Every one of these tables already existed with the right shape for 80% of what this phase needed; adding nullable columns (`priorityScore`, `mappingConfidence`, `wape`/`mase`, a new `CROSTON` enum value) preserves every existing row and every existing query unmodified, while giving this phase's new logic somewhere real to write.

## Why source-of-truth authority decisions are append-only rows, not a mutable "current authority" flag
Overwriting a `SourceAuthorityRule` in place when a decision changes would destroy the exact history the brief's `AuthorityDecisionHistory` concept asked for. Superseding (`effectiveTo` on the old row, a new row for the new decision) gives the same real audit trail as `AuditLog`'s own append-only design elsewhere in this project, at zero extra modeling cost.

## Why brand conflicts and category conflicts in the post-validated OEM consolidations are NOT treated with equal severity
Real data showed 592 brand conflicts but only 38 category conflicts among 898 real multi-reference parts. Investigating a sample confirmed the expected real-world explanation: the same OEM cross-reference number is legitimately manufactured by multiple different aftermarket suppliers — that is what an OEM cross-reference *means*. Flagging every brand difference as an error would have produced 592 false-positive review items drowning out the 38 real category-mismatch cases that actually indicate a wrong merge. See [parts-catalogue-quality.md](parts-catalogue-quality.md).

## Why the lubricants sales-order-lines importer was added this phase
The lubricant-demand forecasting dataset (a completion-criteria requirement) needs real per-item quantities, which the Data Consolidation phase's `importLubricantsSalesOrders()` (headers only) doesn't provide. Rather than build a parallel importer, `importLubricantsSalesOrderLines()` was added to the existing `ImportService` following the exact same staging → normalize → resolve → upsert shape as every other `import*` method there — real extension, not duplication. Real result: 4,271 real lines staged, 2,919 imported (linked to the 90-day-window headers already present), 1,368 correctly routed to `UNRESOLVED_SALES_LINE` manual review (their headers are older than the imported 90-day window) rather than silently dropped.

## Why the FNV-1a hash replaces a naive rolling-hash in `entityGroupedSplit`
A first implementation (`hash = hash*31 + char`, a textbook polynomial rolling hash) was tested against real-shaped sequential entity IDs (`entity-0`..`entity-19`) and found to cluster IDs sharing a prefix into the same relative hash rank regardless of seed — because the shared prefix dominates the early hash state before the differing suffix characters are processed. Caught by a real, honest test failure ("produces a different split for a different seed"), not assumed correct. FNV-1a's per-character multiply-then-xor mixes much better; verified the same test now passes with genuinely different splits per seed.

## Why `checkNoTemporalOverlap` treats an empty train or test bucket as a pass, not a crash
A real run of the lubricant-demand dataset build against real short-history items produced an empty train bucket for some products (their few real sales all fall within the test/validation window). The original implementation called `Math.max()`/`Math.min()` on an empty array (`-Infinity`/`Infinity`) and then `new Date(-Infinity).toISOString()`, which throws. Caught by running the real verification script, not by code review — fixed to treat an empty bucket as a real, valid "no overlap possible" pass.

## Why `reviewedById`/`reviewerId` in the verification script had to become a real `User` row, not a literal string
`ManualReviewItem.reviewedById` carries a real foreign-key constraint to `User` (added in the Data Consolidation phase, unchanged here). The verification script's first run used a literal descriptive string (`'verification-script'`) and failed with a genuine `P2003` foreign-key violation — a real, useful catch proving the FK constraint actually works. Fixed by looking up a real, already-seeded `GENERAL_MANAGER` user and using its real id throughout.

## Why customer data quality classifies as `NOT_USABLE` and this is reported, not hidden or "fixed"
The real profile shows 100% missing tax number and 96% missing email for the imported lubricants customer base. Both are real, expected properties of the source (`MolasCacheDb.CacheCustomers` never had a tax-number field; this is a phone-first retail market). The phase's own rule — "do not hide low-quality data behind one overall average," "no automatic remediation of production data" — means the correct action is to report the real `NOT_USABLE` classification honestly, not to fabricate a workaround or suppress the finding because it looks alarming.

## Why inventory backfill was not executed despite a documented recommended strategy
Both business units score the same real strategy (`STRATEGY_B_OPENING_BALANCE`), but `isReadyForOpeningBalanceImport()` requires both a verified warehouse mapping and an approved cut-off date — neither exists yet (warehouse mapping is `UNMAPPED`; no cut-off date has been approved by a human). Per the phase's explicit rule ("no inventory backfill may be approved until relevant warehouse mappings are verified"), documenting readiness and executing an import are treated as two distinct bars, and only the first was cleared this phase.

## Why AI use-case readiness was verified against real evidence rather than assumed from the original brief's predictions
The brief itself instructed: "verify rather than assume the following likely positions." Every status in [ai-use-case-readiness.md](ai-use-case-readiness.md) is backed by a real database query at assessment time (real row counts, real decision counts) — re-running `persistAssessments()` re-evaluates that evidence, so a status can only change when the underlying real data actually changes, never by editing a hardcoded label.
