# Data Consolidation — Decision Log

Short entries — the reasoning behind choices that weren't the only reasonable option. Same format as the root [decision-log.md](../architecture/decision-log.md).

## Why source databases remain read-only despite the `sa` credential having full write access
The only SQL Server credential provided is `sa` — a sysadmin login with unrestricted access to the entire instance. Rather than block on requesting a scoped login before doing any real work, every adapter (`MolasLubricantsCacheAdapter`, and the profiling scripts before it) was written to issue `SELECT` statements only, with the read-only guarantee enforced by code discipline and documented explicitly as a risk (see [docs/data-sources/source-data-risks.md](../data-sources/source-data-risks.md) §1) rather than left unstated. A scoped `db_datareader` login remains a real, actionable recommendation for whoever administers that SQL Server instance.

## Why staging is mandatory, not optional
Every prior phase's sync convention (Vehicle/Part/Customer/Supplier/LubricantProduct) went straight from a validated, normalized raw record to a domain upsert — fine when the source's shape was already well understood (Phase 1's own `FileDropAdapter`) or built alongside the domain model (Phase 2's sales/purchase document import). Here, real production sources were being profiled for the first time in this codebase, with genuine surprises (an empty database where one was expected, a populated one nobody had named, duplicate keys, sentinel dates). Staging every record first, with its own validation/normalization/matching status, means a wrong assumption in the matching logic can be found and fixed by re-processing already-staged data — no re-extraction from the live source needed, and no partially-wrong domain row created in the meantime.

## Why `IntegrationSource`/`SyncRun` were reused instead of building `ImportBatch`
`IntegrationSource.name` has been a globally unique feed identity since Phase 1; `SyncRun` already carries `cursorBefore`/`cursorAfter` and per-run counts. Building a parallel `ImportBatch` model would have duplicated exactly the checkpoint/batch-accounting machinery already proven correct across every other integration in this codebase, for no benefit — and the phase's own "avoid the cursor-collision bug" concern is already resolved by `IntegrationSource.name`'s existing uniqueness constraint. Two nullable columns (`extractionMode`, `schemaVersion`) were added to carry this phase's extra metadata rather than inventing a second checkpoint table.

## Why `SourceSnapshot` and `SourceSchemaSnapshot` were merged into one model
The original brief listed them separately. In every real profiling run performed in this phase, schema and approximate row-count stats were captured and compared together (a column being added/removed is itself a stats-relevant event) — modeling them as two tables would mean joining them back together on every read for no real independent use case observed.

## Why `PartExternalReference`/`WarehouseExternalReference`/`BranchExternalReference` were added, mirroring existing tables exactly
`Customer`, `Supplier`, and `LubricantProduct` already had a `*ExternalReference` table giving them real multi-source canonical identity (built in Phase 2, before this phase existed). `Part` didn't. Rather than design a new pattern, the exact same shape was added for `Part` (and, since branch/warehouse resolution needs the same multi-source-code mapping, for `Warehouse`/`Branch` too) — consistency over novelty.

## Why customer/parts/lubricant matching never auto-merges below HIGH_CONFIDENCE
Real data proved this wasn't a hypothetical concern: 241 of 4,247 real lubricants customers (≈5.7%) had only a name-level or conflicting-signal match against an existing record. Auto-merging any of those would have risked silently combining two real, distinct businesses (or splitting one real business's history across two records) based on nothing stronger than a shared name or phone digit sequence. Every POSSIBLE_MATCH/CONFLICT is a `ManualReviewItem`, decided by a person.

## Why generic/walk-in customer codes are never used as a matching signal
Real profiling found `CardCode = "0001"` recurring across many `NeonAutoHubSalesOrders` rows, and codes like `"b00000000"`/`"C00000000"` in `CacheCustomers` — clearly placeholder/walk-in codes, not real party identifiers. `isGenericCustomerCode()` exists specifically so these never get treated as a real customer identity signal, which would otherwise silently merge hundreds of unrelated walk-in sales into one fictional mega-customer.

## Why AutoHub sales orders use `unresolvedCustomerRef` instead of fabricating a customer record
`Parts_Catalog` has no dedicated AutoHub customer-master table — only `CardCode`/`CardName` embedded directly in each sales/invoice/delivery header. Creating a `Customer` row from a document header alone (rather than a real customer-master extraction) would risk creating a customer record with stale, header-snapshot data instead of the source's actual current customer record. The existing `SalesDocument.unresolvedCustomerRef` field (already part of Phase 2's design, for exactly this situation) preserves the real code without fabricating an entity around it.

## Why oitm's duplicate `item_code` values collapse at the staging layer rather than being separately preserved
`oitm.item_code` has 316 duplicate values across 9,154 real rows (profiling finding). This pipeline's feed key for the `oitm` extraction is `item_code`; re-extracting a duplicated code overwrites the same `RawSourceRecord` row (last-write-wins for staging purposes). This was an accepted, documented trade-off for this pass's goal (item master consolidation) rather than a bug fix, since the OEM-number-based matching in `PartConsolidationMatchingService` is what actually resolves the real-world duplicate (see [parts-consolidation.md](parts-consolidation.md)'s `VAG10769`/`VAG13636` example) — the staging-layer collapse only affects which specific raw row's incidental fields (rather than which real part) get used when two rows share an `item_code`, which the real data suggests doesn't happen independently of the OEM-duplication case already being handled.

## Why stock/inventory reconstruction was documented but not executed
Committing an inventory opening balance is effectively a one-way door for Phase 2's inventory ledger — an incorrect cut-off snapshot is expensive to unwind and would corrupt every downstream analytics/forecasting/recommendation computation built on top of it (Phases 2 and 4). Neither real source supports full historical ledger reconstruction (Strategy A); Strategy B (opening balance + future movements) is the recommended path once a cut-off date and warehouse-code mapping are explicitly approved — a decision this document surfaces rather than makes unilaterally.

## Why branch/warehouse resolution wasn't wired to real source codes in this pass
Real warehouse codes seen in `MolasCacheDb.CacheProducts.WarehouseCode` (`"01"`, `"COCWHSE"`, `"MainWHSE"`) have no obvious, safe-to-guess mapping to this system's existing `Warehouse` rows (created in Phase 2 from a different naming convention). `WarehouseExternalReference`/`BranchExternalReference` exist and are ready to hold that mapping the moment someone who knows the real correspondence (e.g. "COCWHSE = the Coca-Cola Road branch's main warehouse") confirms it — guessing would risk misattributing real stock/sales figures to the wrong physical location.

## Why manual-review approval records the decision but doesn't yet auto-execute the merge
`ManualReviewItem.approve()` currently marks the review APPROVED with a reason, but a human (or a follow-up script) still performs the actual entity link/merge. Auto-executing on approval would need the approval action itself to carry enough structured information to safely replay the exact proposed change — reasonable to build once the review UI/workflow that produces that approval exists, but premature to build against an API-only approval path with no real reviewer UI yet.

## Why purchase-order import and full historical (>90-day) sales/invoice import were not executed this pass
The phase's own historical-backfill guidance is explicit: start with a limited window, reconcile, then expand — not import everything in one pass. The 90-day sales-order slice already proves the pipeline (staging, matching, reconciliation, idempotency, safe update, cursor safety) end-to-end against real data; expanding the window or adding more document types is now a matter of repeating an already-proven pattern, not new design work.

## Why AI training must wait for validated real data
This phase exists specifically so that Phase 4's AI layer (RAG, forecasting, purchasing signals) eventually learns from reconciled, traceable, real data rather than a mix of Phase 1-4 synthetic test fixtures and unvalidated real imports. Wiring AI consumption of this newly-imported data before its reconciliation/manual-review backlog (241 pending customer reviews) is cleared would mean training on data this phase itself flagged as not-yet-trustworthy.
